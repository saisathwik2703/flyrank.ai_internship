Which pages should be reviewed first for content refresh?

An explainable content-opportunity ranking workflow that compares a transparent rule baseline with learned models, while keeping validation, leakage control, and public-safe reporting explicit.

Abstract

This project asks which content pages should be reviewed first when editorial capacity is limited. It uses the FlyRank ML Internship data framework, whose warehouse release contains 78,835,655 daily performance rows plus pseudonymized content and client dimensions, while the reproducible benchmark reported here uses the repository’s verified 30,000-row anonymized starter slice. A transparent refresh-opportunity rule is compared with logistic regression, a decision tree, and a random forest under the same client-holdout evaluation design, with identifiers excluded from features and leakage-prone fields treated conservatively. On the verified starter benchmark, Precision@50 rises from 0.24 for the baseline to 0.74 for the random forest, with ROC AUC rising from 0.627 to 0.750. The result supports a decision-support workflow for prioritizing human review, not a claim that editing a ranked page will cause recovery or that the model predicts Google’s algorithm.

Scope note. The public repository currently contains blank Week 5–7 personal notebooks. Therefore this page reports only metrics already verified in the repository’s committed starter benchmark and does not pretend that a new full-warehouse model run was completed.

Introduction / Problem statement

A content team can inspect only a small fraction of its inventory at a time. The practical decision is therefore not “which pages are bad?” but “which pages deserve human review first?” A useful ranking should combine evidence of demand, deterioration or opportunity, and sufficient data quality while still giving a reviewer a reason they can inspect.

The unit of analysis is a content page. The output is a ranked review queue with scores and reason codes. The main cost of a wrong high-priority call is wasted editorial time; the main cost of a missed positive is delaying attention to a page that might deserve investigation. For that reason, top-of-queue precision is a central metric.

Methodology

Target and assumptions

The starter benchmark uses is_declining_label = (trend_direction == "down"). This is a deliberately simple proxy derived from the current observation window, so it is suitable for demonstrating the workflow but weaker than a production-quality future-window target. A stronger warehouse capstone should use prior-window features to predict a later-window decline or recovery without overlap.

Baseline

The transparent baseline combines visibility, freshness risk, position opportunity, and content-depth gap:

baseline_refresh_score =
  0.40 * visibility_score
+ 0.30 * freshness_risk_score
+ 0.25 * position_opportunity_score
+ 0.05 * depth_gap_score

Reason codes include stale visible pages, declining pages with demand, thin visible pages, page-one decay risk, low-CTR visible pages, and low-engagement visible pages.

Models and validation

The benchmark compares logistic regression, decision tree, and random forest against the baseline on the same split. Client-holdout validation keeps whole clients out of training so performance is measured on clients unseen by the model. Evaluation uses ROC AUC, average precision, and Precision@50 because the operational need is ranking the most useful review candidates near the top.

Leakage controls

Client/content/hash IDs are excluded as predictive inputs. Product decision scores or flags are not used as features or labels. Any future-window measurements must remain outside the feature window, and current-window derived fields such as trend_direction or trend_pct should be excluded when they directly define a future target or otherwise leak the answer.

Limitations & honest framing

The strongest limitation is scope: the published metrics are from the 30,000-row starter slice, not a fresh model run over the full ~78.8M daily facts. The starter label is also a current-window proxy, so it demonstrates ranking workflow quality rather than future outcome prediction. The warehouse history is an unbalanced panel, meaning clients have different tracking start dates; missing tracking must not be interpreted as zero performance.

The analysis is observational and supports prioritization, not causal claims. A high-ranked page is a candidate for review, not a guarantee that editing it will improve search performance. Real decline can also be confused with consolidation, seasonality, SERP changes, or low-volume noise, so human review remains necessary.

Ranked recommendations

  1. Review visible pages with sustained decline first. Require meaningful impressions/demand and enough history to distinguish persistence from a short-lived fluctuation.
  2. Protect page-one performers showing decay risk. Pages already near the top can have higher opportunity cost if deterioration continues, but inspect seasonality and query mix before acting.
  3. Investigate low-CTR pages with meaningful visibility. Compare CTR in the context of average position and impression volume rather than treating low CTR alone as failure.
  4. Inspect stale or thin pages only when evidence shows demand. Age or word count should be reason codes, not standalone proof that a refresh is needed.
  5. Keep a human in the loop and monitor drift. Re-check precision, base rate, client coverage, feature distributions, and reason-code mix when the release window or traffic environment changes.
Intended use: decision support for editorial triage. Not intended for: autonomous editing, causal attribution, reconstructing private identifiers, or claiming knowledge of a search engine’s ranking algorithm.

Reproducibility

The repository contains the reference pipeline and Week 1–8 notebook skeletons. The starter benchmark can be rerun from a fresh clone with:

git clone https://github.com/saisathwik2703/flyrank.ai_internship.git
cd flyrank.ai_internship
pip install -r requirements.txt
python scripts/run_all.py

Primary links: repository, capstone notebook, and the committed example outputs.

For a full warehouse rerun, use the fixed 2026-07-03 release and preserve the same feature/target window definitions, grouped or time-aware validation, and explicit leakage audit.
